# Matcha-TTS を日本語（JVS 100話者）で事前学習する

## 初めに

日本語 TTS を自前で学習する取り組みの一環として、非自己回帰の高速 TTS である **Matcha-TTS**（条件付きフローマッチング, ICASSP 2024）を **JVS コーパス（日本語100話者）で事前学習**した。

Matcha-TTS はテキストからメルスペクトログラムを ODE ベースのフローマッチングで生成し、ボコーダで波形に変換する。速く・軽く・CPU/モバイル配布も現実的という利点がある一方、公式設定は英語（LJSpeech / VCTK）のみで、**多話者日本語の学習知見はほとんど公開されていない**。実際にやると英語では起きない問題に何度もぶつかったので、詰まった点と、その後に試した音質改善の検証（そのほとんどが実測で棄却された）をまとめて残す。

MAS まわりの退化は、piper-plus 等の VITS 系を触っている人には馴染みのある話題だと思う。今回は Matcha-TTS で同様の退化に正面からぶつかった記録でもある。

## 結論

先に要点を書く。

- 最大の詰まりは **MAS（Monotonic Alignment Search）のアライメント退化**。多話者 × 日本語55音素という条件で、学習サンプルの **39〜43%** がアライメント崩壊した。学習量を5倍にしても悪化する、アルゴリズムレベルの問題だった
- 対策は **Julius 外部アライナーで duration を事前計算**して MAS をバイパスする方法。これで退化率 0% を達成した
- 「良さそう」で試した最適化の多くは **実測で棄却**された（FP16、LR スケジューラ、logit-normal sampling、out_size 切り出しなど）
- 評価で一番の学びは「**UTMOS は万能ではない**」。UTMOS は内部で 16kHz にダウンサンプルするため、8kHz 超の高域改善を原理的に測れない
- ボコーダをどう変えても「濁り」は取れなかった（独立2実験で確認）。むしろ日本語データで学習したボコーダが汎用ゼロショットに負けた（ドメインミスマッチ）

## 開発環境

- Python 3.12（uv で管理）
- PyTorch 2.10 + cu128
- GPU: RTX 5090 × 4（DDP、事前学習）/ 単一 RTX 5090（ボコーダ・fine-tune、vast.ai）
- g2p: pyopenjtalk-plus + onnxruntime
- 精度: bf16-mixed
- データ: JVS ver1（100話者、約13,000発話）

## Matcha-TTS の構成

Matcha-TTS は以下の構成を取る。

```
テキスト → 音素列（+ブランク挿入）
  → TextEncoder（Conformer + RoPE + Duration Predictor）
  → 予測 duration でメル長に展開
  → CFM Decoder（Euler/Midpoint ODE ソルバー, n_timesteps ステップ）
  → メルスペクトログラム → ボコーダ → 波形（22050 Hz）
```

非自己回帰なので速く、ODE のステップ数（デフォルト5前後）で品質と速度を調整できる。

## 日本語対応（テキスト→音素）

英語の espeak-ng 経路とは別に、日本語は **pyopenjtalk-plus** を使う。

- **55シンボルの日本語語彙**（英語は178）。フルコンテキストラベルから音素と韻律記号を抽出する
- 韻律記号は **ttslearn の `pp_symbols` / ESPnet の `pyopenjtalk_g2p_prosody` 準拠**にした。アクセント境界 `[` `]`、句境界 `#`、疑問文末 `?` を対応する音素の直後に出力する
- 疑問文（例:「元気ですか？」）は文末 sil を `$` ではなく `?` にする

ここで一点、あとから効いてくる注意がある。韻律記号の位置（直前か直後か）や1音素あたりのマーカー数を変えると、音素列長が変わる。**cleaner の仕様を途中で変えると学習済みモデルとの互換が壊れる**（エラーは出ないが品質が劣化する）ため、序盤で仕様を固定しておくべきだった。

なお DNN アクセント推定の **MARINE は調査の上で不採用**とした。公開モデルは JSUT のみの学習で論文精度に届かず、メンテナー自身が「ルールベースの方が精度が高い傾向」と明言している。JVS 実テキストでクラッシュも確認した。アクセント誤りはユーザー辞書（推論時の入力補正で再学習不要）で対処する方針にした。

## 事前学習のレシピ

原論文に忠実な設定が結局いちばん安定した。

| 項目 | 値 | 補足 |
|------|------|------|
| 精度 | bf16-mixed | FP32 比 +11% steps/sec |
| out_size | null（全長メル） | 172 に切ると品質劣化 |
| 学習率 | 1e-4 固定 | scheduler なし、weight_decay=0 |
| timestep sampling | 一様分布 | logit-normal は品質劣化 |
| EMA | decay=0.9995 | epoch 10 から |
| Loss | duration + prior + flow-matching を重み1.0で均等 | 原論文準拠 |
| max_epochs | 2500（約240Kステップ） | 原論文500Kの約半分 |

bf16-mixed 時は `optimizer.fused=false` が必須だった。fused AdamW と mixed precision と gradient clipping の組み合わせはクラッシュする。

## 詰まったポイントと解決 (1): MAS アライメント退化

ここが今回の本題である。

### 症状

学習を進めても音がはっきりしない。調べると、MAS が生成するアライメントが構造的に退化していた。

- 学習サンプルの 39〜43% で、音素の80%以上が「1フレーム」に潰れる
- 代わりに先頭の blank[0] にフレームが集中する（退化時は平均101フレーム、正常時は4フレーム）
- Duration Predictor はこの退化ターゲットを忠実に学習し、推論時に各音素が約2フレームしか割り当てられず発音が不明瞭になる

### 学習量では直らない

| | 500 epoch | 2500 epoch |
|------|:---:|:---:|
| ステップ数 | 48K | 240K |
| MAS 退化率 | 39.2% | 43.0%（悪化） |

5倍学習して悪化した。学習量の問題ではなく、アルゴリズムレベルの問題だと判断した。

### 根本原因

MAS は log_prior（ガウシアン距離 `-½‖y - μ_x‖²`）に基づく貪欲 DP である。正しく働くにはエンコーダ出力 μ_x が音素ごとに十分異なる表現を持つ必要がある。ところが、

- 多話者設定ではエンコーダが100人分の声を同一空間に圧縮するため μ_x が平均化され、blank と音素の区別が消える
- 日本語55音素は英語178音素より粗くモーラ寄りで、音素間の音響差が小さく退化を加速する（英語 VCTK で退化が報告されないのはこの粒度差が大きいと考えられる）

数値で見ると、退化サンプルのエンコーダ μ_x ノルムは 2.06〜2.26、正常サンプルは 6.14〜7.81 だった。表現が潰れているのが定量的に見える。

### 解決: 外部アライナーで MAS をバイパス

結論は「MAS を使わない」だった。Julius forced aligner で音素 duration を事前計算し、`use_precomputed_durations=true` で学習する。コードベースには元々このパスがあり、MAS ブロックをスキップして `generate_path(durations)` で直接アライメントを生成する。

- Julius segmentation-kit で JVS 各発話をアライメントし、`.lab`（音素の開始/終了時刻）を得る
- Julius 音素 → pyopenjtalk 55シンボルへのマッピングテーブルを作成する（促音 cl・撥音 N・ポーズ・韻律記号の扱いを整合させる）
- 時刻をフレーム数に変換し（`frames = (end - start) × sr / hop`）、ブランク挿入後の音素列長と一致させる

これで退化率 0% となり、全品質ゲートを通過した。Julius + Matcha-TTS の日本語パイプラインは名古屋大戸田研の JATTS が先行実証していたのも後押しになった。

日本語 × 多話者 × 粗い音素セットという条件は MAS 退化を顕在化させやすい。VITS 系を含め、同条件なら外部アライナーを最初から検討する価値がある。

## 詰まったポイントと解決 (2): 効かなかった最適化

「良さそう」で試して品質が劣化したものを、同じ轍を踏まないように残す。

| 試したこと | 結果 |
|------|------|
| FP16 mixed precision | Loss を FP32 キャストしても Duration Predictor 品質が劣化。encoder/decoder 内部表現の FP16 精度不足が原因で、NaN 防止だけでは不十分 |
| LR スケジューラ（warmup+cosine） | cosine decay が DP の収束を妨げる。原論文は固定 lr |
| Logit-Normal timestep sampling | t≈0,1 の学習不足でデコーダ出力に正バイアス |
| out_size=172（切り出し） | DP が内部音素に1フレームしか割り当てず発音不明瞭 |
| prior_loss 重み 0.5 | encoder μ_x 品質低下 → デコーダ条件付け劣化の連鎖 |
| torch.empty で切り出し | 未初期化メモリで NaN 混入。torch.zeros が必須 |

bf16 は FP16 とは別物で、8bit 指数部を持ち overflow しないため、上記 FP16 の問題は該当しない。ここは混同しやすい。

## ボコーダ改善: WaveNeXt と ONNX 化

音響モデルがボコーダ天井（UTMOS 3.00 が汎用 HiFi-GAN の 2.90 とほぼ同等）に到達したので、ボコーダ側を検討した。

- 調査の結果、mel 仕様が完全一致する公開ボコーダを複数見つけた。ONNX 配布を基準に **WaveNeXt** を選定した
- Vocos は iSTFT が ONNX 非対応で単一グラフに埋め込めない。WaveNeXt は iSTFT 無し（ConvNeXt + 線形ヘッド）なので非対応 op ゼロで埋め込める
- Matcha + WaveNeXt を単一 ONNX グラフ化でき、CPU RTF 0.093（実時間の約1/10）で合成できた

CPU/モバイル配布を狙うなら、ボコーダの iSTFT 有無は最初に確認すべき点だった。

## 検証: fmax 引き上げ（客観と体感の乖離）

「濁り」の原因を fmax=8000 の構造天井（メル上限周波数）と仮説立て、fmax=11025 を検証した。

交絡を排除した A/B を組んだ。同じデータ・同じステップで、fmax だけ変えた2本のボコーダを学習し、正解 wav に対する高域（8-11kHz）忠実度を比較する。

| 指標 | fmax=11025 | fmax=8000 |
|------|:---:|:---:|
| 高域 log-STFT L1（低い=良） | 0.825 | 1.031 |
| 高域エネルギー比（1が理想） | 0.851 | 0.553（45%欠損） |
| 40サンプル中 正解に近い方 | fmax=11025 が 40/40 | — |

客観的には fmax 引き上げは明確に効く。データ変更では埋まらない、fmax 独立の効果である。ところが、自分の耳では体感差がなかった。

そのため、mel 統計の再計算・全前処理やり直し・音響モデル全再学習という破壊的変更は見送った。「客観指標が良い」と「採用すべき」は別、という判断である。

この検証中に気づいた重要な事実がある。**UTMOS（SpeechMOS）は内部で 16kHz にダウンサンプルするため、fmax=8000 と 11025 の差（=8kHz 超）を原理的に評価できない。** UTMOS を唯一の指標にしていたらこの判断はできなかった。今回は 8-11kHz の log-STFT L1 とエネルギー比という自作指標で測った。指標が「見ていない」領域を意識するのは大事だと痛感した。

## 検証: 日本語ボコーダのドメインミスマッチ

もう一つ直感に反する結果があった。音響モデルを固定し、ボコーダだけ差し替えた3-way 比較（UTMOS）である。

| ボコーダ | UTMOS |
|------|:---:|
| WaveNeXt 汎用ゼロショット（多言語） | 3.049 |
| HiFi-GAN univ（現行） | 2.945 |
| WaveNeXt 日本語データで学習 | 2.586（最悪） |

日本語データ（キャラクター音声コーパス）で学習したボコーダが、汎用ゼロショットに負けた。耳でも UTMOS でも一致した。

理由はドメインミスマッチである。学習に使ったのはキャラクター声、評価は JVS 朗読声だった。「同じ言語」でも「同じ音響ドメイン」ではない。汎用ボコーダの方がドメイン非依存で頑健だった。ボコーダは「鳴らす音声のドメイン」に合わせるべきで、in-domain 言語データで学習すれば良い、は必ずしも成り立たない。

この結果と過去の BigVGAN 検証を合わせ、「濁りはボコーダをどう変えても取れない」ことが独立2実験で確定した。濁りの主因はボコーダではなく、音響モデルの予測 mel 側かコーパスの本質的特性にあると考えている。

## 単一話者 fine-tune の壁

最後に、事前学習済みモデルから単一話者への fine-tune を試した。既存の日本語100話者モデルを土台に、話者 embedding を 100→101 に拡張し、約100発話の単一話者コーパスで約33分 fine-tune した。

結果は「似てはいるが、まだ足りない（声質が寄りきらない）」だった。

学習後の話者 embedding（新スロット）を初期化値（既存話者の平均）と比べると、次のようになっていた。

```
cos類似度 = 1.000,  L2距離 = 0.031
```

話者 embedding がほぼ全く動いていない。fine-tune は走ったが、話者表現が初期値（平均声）付近に留まっていた。だから平均っぽい声に聞こえる。

なぜ動かなかったのか、真因はまだ特定できていない。候補は EMA（decay=0.9995）による平滑化、条件付け次元の弱いレバー、100発話という小データ、平均 init が低勾配の谷になっている、などが考えられる。ここは勾配ノルム測定・EMA off・LR 引き上げといった追加 ablation が必要で、後日詰める予定である。安易に原因を断定しないでおく。

Matcha-TTS 系で単一話者に fine-tune するときは、話者 embedding が本当に動いているかを測るのは一手間の価値がある、というのが現時点の教訓である。

## まとめ

やってみて分かったことを整理する。

| テーマ | 学び |
|------|------|
| MAS 退化 | 日本語 × 多話者 × 粗い音素セットで顕在化。学習量では直らない。外部アライナー（Julius）でバイパスする |
| 精度 | bf16 は問題ないが FP16 は DP 品質を壊す。原論文レシピ（固定 lr・out_size=null・均等 loss）が結局安定 |
| fmax | 客観的には効くが体感差ゼロなら破壊的変更は見送る。UTMOS は 8kHz 超を見ない |
| ボコーダ | 汎用ゼロショットが頑健。「同じ言語」は「同じドメイン」ではない。濁りはボコーダでは取れない |
| 単一話者 fine-tune | 話者 embedding が動かない現象がある。測って確認すべき |

一番伝えたいのは、良さそうな改善の多くが実測で棄却されたという点である。指標を疑い（UTMOS の限界）、交絡を排除した A/B を組み、最後は自分の耳で判断する。地味だがこれが一番効いた。
